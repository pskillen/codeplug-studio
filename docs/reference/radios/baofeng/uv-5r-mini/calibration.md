# UV-5R Mini calibration (`0xF000–0xFFFF`)

## Purpose

Field layout of the Mini's calibration sector as the read-only viewer on `/debug/uv5r-mini` decodes it. Every field comes from a **static trace of the v0.04 `app.bin`** (radio repo PR #219, ledger F302-F309); v0.27 runs the same code relocated (same loader read order, same PA table, same defaults). Nothing here is validated on hardware, no value from a real radio is quoted (shape only), and none of it is permission to write the sector: the debug page is read-only and its sender refuses `W`/`D`.

**Confidence.** Each field carries one of: _traced_ (code address and meaning), _partly traced_ (traced use with an inferred meaning or name, marked "inferred"), or _unknown_. Bytes that nothing reads are **unused (no reader)**, never unknown. No byte of this sector is free space: a `W` at `0xF000` erases all of it.

## Behaviour

- **PA bias is per power frame, not per segment.** The loader scatters the twelve rows into RAM and a table picks them by band; the PC tool stores one 64-byte frame per power index. The index is the VFO frame's power byte. Studio's earlier viewer assumed segment-major order and labelled every row with the wrong band or level; it now reads power-major.
- **Squelch.** Open and close thresholds are by level 0-9, minus a per-frequency offset. Below 130 MHz (airband) and at 180-199 MHz the firmware ignores the level: it sets the open threshold from the level-9 entry and close = open − 3 (`0x1E50F1C`). The units of the thresholds (dB) need a bench.
- **Band edges come from the region byte, not from `F230`.** `0x19DA4-0x19DC7` are written only by the loader, from built-in tables at `0x1E5E0E0+` selected by `F255`. `F230` is the CPS-facing copy the `F` reply sends; for the default region the firmware's fourth RX band is 350-390 MHz while `F230` advertises a narrower one.
- **Frame residue.** The calibration was written as ten whole clone frames (`F000-F27F`) from one buffer: 64-byte copies of other rows over the unread bytes match exactly on two radios. The cause is inferred (the tool is not in hand). Any write tool that "restores" calibration would have to reproduce whole frames, and a byte compare of two radios will differ in residue bytes that mean nothing. No stock code writes `0xF000-0xFFFF`; only the clone `W` and `D` handlers can.

## Counts (the viewer's layout)

| Role                            | Ranges / fields                                          | Bytes |
| ------------------------------- | -------------------------------------------------------- | ----- |
| Fields, traced                  | 21                                                       | 316   |
| Fields, partly traced / unknown | 0 / 0 (the level-2 name is inferred inside the PA field) | 0 / 0 |
| Frame residue (no reader)       | 10 ranges: 6 + 6 + 3 + 224 + 10 + 1 + 4 + 17 + 11 + 42   | 324   |
| Erased, unused                  | 1                                                        | 3,456 |
| Still unknown                   |                                                          | 0     |

316 + 324 + 3,456 = 4,096. Inside the fields, some bytes have no reader: the unused tails of the squelch-offset rows and the PA rows (see the "used" counts above) and five flag bytes of the band limits. The research report's "309 bytes of residue" counted only the ranges Studio previously showed as untraced; the viewer's 324 adds the 12 residue bytes in the old "partly traced" range and `F11D-F11F`.
