# RT95 debug memory capture

The debug read uses the existing guarded PROGRAM/QX session. It reads the two chip guard probes at `0x3B00` and `0x7B00` before attempting the MMD1 region. A refusal leaves the clone and calibration capture intact and records the reason and raw probes. On success it reads `0x4000–0x5FFF` as 512 aligned blocks into the inspect-only `rt95-mmd1` region. It sends no EEPROM write frames. Coverage remains partial and is not a physical backup.

MMD1, zone names, membership and ZST1 state are decoded with the existing radio codecs. Each member bitmap index maps to a one-based clone slot. Captured zones do not depend on clone availability. State validity is separate from zone validity. The viewer identifies P-key DIR as a stored value that compatible firmware uses as ZON; it cannot detect running firmware or a release. A compatibility claim requires a valid table and verified raw guard evidence.

Main-body EEPROM is reached through the head. The head can return checksum-valid zeros without a body reply, and can also return the previous block or a shifted block with a valid checksum (see [calibration](calibration.md)), so captured bytes are not proof of a physical body response. Clone fields have unknown provenance and PC ident comes from the head. Hardware verification remains outstanding; fixtures are synthetic.

See [MMD1 layout](mm9pdy-data.md), [calibration](calibration.md) and [radio debug](../../../../features/radio-debug/README.md).

The clone inventory covers 200 ordinary slots, with occupancy and scan bitmaps, wire names, frequencies, raw duplex/offset, TX state, power, exact width, tones, signalling indexes and raw 32-byte records. Invalid encodings and missing bytes remain visible. Duplex 3 on ordinary slots has unproven TX semantics. Custom CTCSS uses the 0.1 Hz word. Search and sort use slot and wire name; the empty-slot control exposes empty slots. Validated descriptions require the shared CRC and fingerprint checks and supplement the wire name. The Memory tab's Settings view decodes every field in the settings registry (73 fields, the same list Write overrides use; see [settings](settings.md)) from the clone image, grouped by the registry's sections, with address, mask, raw bytes (behind a toggle), decoded value or "not interpreted", the trust tag (CPS, CHIRP or both), the advanced flag and the stock / MM9PDY targets. A field is shown only when every byte of its span was captured. The registry covers 377 of the 512 bytes in the two settings windows (`0x1980-0x1AFF`, `0x3200-0x327F`); the other 135 bytes are listed as named read-only runs: 42 with a meaning (side A/B channel index and flags, tone group 0 byte 0, stun/kill digits 15–16, DTMF auto reset, key brightness, mic keys, mic level, band copy, DTMF in-use mask), each with a confidence, and 93 **unused (no reader)**. None is in the Write registry. See [settings](settings.md#bytes-outside-the-registry-debug-only). The power-on password digits and their raw bytes are masked until **Show password** is pressed (the same `useSensitiveReveal` state as Hex and Compare). The view is read-only. VOX enable is bit 0 in the registry; the older retain preview uses bit 7. All clone values have unknown provenance.
