# Orchestrator instructions: modded firmware flasher

You are running the 4-phase modded firmware flasher series (epic
[#1358](https://github.com/pskillen/codeplug-studio/issues/1358)). Read [00-README.md](00-README.md) for the phase
table. Each implementor reads its own phase file; you only read enough to brief it.

This delivery model has no track record in this repo. Treat these instructions as a reasoned first attempt, and
record what didn't work in `zz-final-handover.md`.

## Your container is fresh every time you resume

At the start of every turn where you act:

```bash
git fetch origin --prune
git fetch origin plan/modded-firmware-flasher
rm -rf "$HOME/plan-ref"; git worktree prune
git worktree add --detach "$HOME/plan-ref" FETCH_HEAD
```

Your state is on the remote:

- the phase branches and PRs;
- **your log**, `tmp/features/modded-firmware-flasher/plans/orchestrator-log.md` on the planning branch.

Read the log first.

After every step that matters, append an entry: phase, branch, head SHA, PR URL, deviations, gate status (with the
owner's words) and decisions. Commit it:

```bash
git -C "$HOME/plan-ref" checkout -B plan/modded-firmware-flasher FETCH_HEAD
git -C "$HOME/plan-ref" add -f tmp/features/modded-firmware-flasher/plans/orchestrator-log.md
git -C "$HOME/plan-ref" commit -m "chore(plan): log phase N <step>"
git -C "$HOME/plan-ref" push origin plan/modded-firmware-flasher
```

Never put product code on that branch, and never merge it.

## Loop for phase N

1. **Preconditions.**
   - Phase N-1's branch is on origin, and its PR is open.
   - Your log shows phase N-1 finished: its gate passed, and for phases 3 and 4 its prod-flip commit landed. Or the
     owner said to continue after a review.
   - Phase 4 starts only after phase 3's flip commit exists, because it stacks on the full phase 3 branch.
2. **Spawn one `implementor`** (worktree isolation) with template A from
   [AGENT-INSTRUCTIONS.md](AGENT-INSTRUCTIONS.md). Fill in:
   - N, the branch, the start ref, the PR base and the PR body lines (table above);
   - **"Prior phases"**: what earlier phases actually shipped, every deviation, the gate results, and the owner's
     decisions.
3. **Wait for it.** You need a PR URL and a head SHA. Check the branch on origin. If it failed, or deviated in a way
   that affects later phases, stop and tell the owner. Don't improvise.
4. **No hardware gate (phases 1 and 2):** stop and notify the owner. Give the PR URL, a summary and the deviations. Then end
   your turn.
5. **Hardware gate (phases 3 and 4).** The implementor has pushed the branch to `dev` and returned an owner script.
   - Confirm that `dev` is at the branch head (`git ls-remote origin dev`). If it isn't, push it yourself with
     `git push --force origin <head-sha>:refs/heads/dev`. This epic owns `dev`, so no permission is needed.
   - **Stop and notify the owner** with: the phase, what shipped, the PR URL, deviations, **the owner script
     verbatim**, that `dev` runs `<sha>`, and what happens on OK and on FAIL.
   - End your turn.
6. **On the owner's reply to a gate:**
   - **Phase 3 or 4, OK** (the owner confirms the bundled `1.0.0` flash):
     - log it;
     - post the result on the phase's issues (with the footer). For phase 4, include the measured flash duration and
       frame round-trip timing on #1364;
     - spawn an implementor with **template B**, result OK, on the **same branch**. It adds only the final prod-flip
       commit, pushes, and updates the PR;
     - verify the flip commit is the branch head;
     - stop and notify the owner ("DM-32UV / AT-D890UV prod flag flipped in PR <url>; continue to phase N+1?");
     - end your turn.
   - **FAIL** (any gated phase): spawn template B with result FAIL and the owner's report verbatim. It fixes the
     problem, pushes, and re-pushes `dev`. Then stop again at step 5. **Never flip a prod flag after a failed gate,
     and never start a later phase on one.**
   - **A decision** (for example, a pipe-optimisation request after the D890 gate): log it, and pass it forward to every later spawn.

## Hard no

- Never merge a PR. Never push to `main`. You push only `dev` and the planning branch.
- Never test hardware, and never ask an implementor to.
- Never flip a prod flag without the owner's explicit confirmation of that radio's `1.0.0` flash.
- Never reorder, skip or rewrite phases. Stop and ask instead.
- Never commit vendor firmware, and don't let an implementor do so.
- Spawn only `implementor`.
