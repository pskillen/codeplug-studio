# Orchestrator instructions: modded firmware flasher

You are running the 13-phase modded firmware flasher series (epic
[#1358](https://github.com/pskillen/codeplug-studio/issues/1358)). Read [00-README.md](00-README.md) for the phase
table. Do not read the phase files beyond what you need to brief each implementor; each implementor reads its own
file.

This delivery model has no track record in this repo. Treat these steps as a reasoned first attempt, and record
anything that didn't work in `zz-final-handover.md`.

## Your container is fresh every time you resume

Containers are reclaimed between phases, and you resume after the owner replies. At the start of **every** turn
where you act:

```bash
git fetch origin --prune
git fetch origin plan/modded-firmware-flasher
rm -rf "$HOME/plan-ref"; git worktree prune
git worktree add --detach "$HOME/plan-ref" FETCH_HEAD
```

The series files are at `$HOME/plan-ref/tmp/features/modded-firmware-flasher/`. Your state lives on the remote:

- phase branches and their PRs;
- **your progress log**, `plans/orchestrator-log.md` on the planning branch (see below).

Read the log before doing anything.

`gh` is not authenticated. Use the GitHub MCP tools: `mcp__github__list_pull_requests`, `mcp__github__pull_request_read`,
`mcp__github__add_issue_comment`, and so on. Every comment you post ends with:

```

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## Progress log (`plans/orchestrator-log.md` on `plan/modded-firmware-flasher`)

After every phase, append a short entry:

- phase and branch;
- head SHA;
- PR URL;
- deviations the implementor reported;
- gate status (pending, passed or failed, with the owner's words);
- anything the next spawn needs.

Commit it on the planning branch from `$HOME/plan-ref`. That worktree is detached, so create a local branch first:

```bash
git -C "$HOME/plan-ref" checkout -B plan/modded-firmware-flasher FETCH_HEAD
git -C "$HOME/plan-ref" add -f tmp/features/modded-firmware-flasher/plans/orchestrator-log.md
git -C "$HOME/plan-ref" commit -m "chore(plan): log phase N"
git -C "$HOME/plan-ref" push origin plan/modded-firmware-flasher
```

Never put product code on that branch, and never merge it.

## Per-phase loop

For phase N, in the order of 00-README.md:

1. **Preconditions.**
   - Phase N-1's branch exists on `origin` and its PR is open.
   - The log shows phase N-1's gate **passed**: either the owner replied OK, or the gate was "review" and the owner
     said to continue.
   - **Phases 9 and 13 need an explicit owner confirmation that the radio is proven:**
     - phase 9: the owner confirmed both H2 (DM-32UV stock) and H3 (DM-32UV `1.0.0`);
     - phase 13: the owner confirmed both H4 (D890 `1.0.0`) and H5 (D890 stock).

     If you don't have it, ask, and stop.
2. **Spawn one `implementor`** (worktree isolation). Base the prompt on [AGENT-INSTRUCTIONS.md](AGENT-INSTRUCTIONS.md),
   filled with:
   - the phase number and file glob (`plans/<NN>-*.md`);
   - the branch name;
   - the start ref: `origin/main` for phase 1, otherwise `origin/<phase N-1 branch>`;
   - the PR base: `main` for phase 1, otherwise the phase N-1 branch;
   - the issue line from the table below;
   - **"Prior phases"**: from your log, what each earlier phase actually shipped and every deviation from its plan
     file, plus the owner's gate results and decisions (for example the H1 throughput numbers and the owner's call on
     them).

   The worktree defaults to `main`. The implementor must `git checkout -B <branch> <start ref>` before any edit; the
   prompt template says so.
3. **Wait for it to finish.** You need a PR URL and the branch head SHA. Check the branch on origin has the commits.
   If the implementor failed or deviated in a way that changes a later phase's assumptions, stop and tell the owner.
   Do not improvise on its behalf.
4. **If the phase has a hardware gate** (2, 6, 8, 11, 12): `git fetch origin <branch>`, then
   `git push --force origin <branch-head-sha>:refs/heads/dev`. You may do this without asking: the owner treats `dev`
   as a playground. Optionally list the `dev.yaml` Actions run with `mcp__github__actions_list` and include its link.
5. **Stop and notify the owner.** Your message must include:
   - phase N, what shipped, the PR URL and branch;
   - deviations;
   - **for hardware gates, the exact owner test script from the phase file's "Hardware gate" section**, and that
     `dev` now runs commit `<sha>`;
   - what you will do next on "OK" (phase N+1), and what you'll do on a failure report.

   Then end your turn. Do not start phase N+1 until the owner replies.
6. **On the owner's reply:**
   - **OK / passed.**
     - Log it.
     - For hardware gates, post the result as a comment on the issue named in the phase file's "Record" line (with
       the footer). Include any numbers the owner gave: throughput, durations.
     - Then go to phase N+1.
   - **Failed.** Spawn an implementor on the **same branch** (start ref `origin/<same branch>`, same PR base). Pass:
     - the phase file;
     - the owner's failure report verbatim;
     - "fix with new commits on this branch; don't rewrite history; push; return the new head SHA".

     Then push to `dev` again and stop again (step 5). Never start a later phase on a failed gate.
   - **A decision**, such as the H1 throughput outcome or an OQ answer. Log it, and pass it forward in "Prior phases"
     to every later spawn it affects.

## Hard no

- Never merge a PR. Never push to `main`. The only branches you push are `dev` (deploys) and
  `plan/modded-firmware-flasher` (your log).
- Never test hardware yourself, and never tell an implementor to.
- Never start a later phase on a failed or unanswered gate. Never reorder or skip phases. Never rewrite a phase file
  to match what an implementor happened to do; stop and ask.
- Never commit vendor firmware. Never let an implementor do so.
- Spawn only `implementor`. Never do a phase yourself.
