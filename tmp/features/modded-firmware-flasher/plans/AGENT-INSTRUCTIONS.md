# Agent instruction templates

The orchestrator uses these blocks to spawn an `implementor`. A human can paste them into a fresh `implementor`
session too. Replace every `<…>` placeholder.

## A. Start a phase

```
You are executing phase <N> of 4 of the modded firmware flasher series in pskillen/codeplug-studio.

Your container is fresh. First:
  git fetch origin --prune
  git fetch origin plan/modded-firmware-flasher
  rm -rf "$HOME/plan-ref"; git worktree prune
  git worktree add --detach "$HOME/plan-ref" FETCH_HEAD
Then read and execute exactly one file:
  $HOME/plan-ref/tmp/features/modded-firmware-flasher/plans/0<N>-*.md   (glob it)
It is self-contained. Do not read other phase files, 00-README.md or ../hl-delivery-plan.md unless the phase file
sends you there. Never merge, rebase onto or cherry-pick plan/modded-firmware-flasher into a product branch.

Branch: <phase-branch>, created with: git checkout -B <phase-branch> <start-ref>
  (<start-ref> is origin/main for phase 1, otherwise origin/<prior-phase-branch>)
PR base: <base-branch>  (stacked; not main unless this is phase 1)
Issue lines for the PR body: <from the phase file>

Read AGENTS.md and DESIGN.md first. Confirm the start ref contains the prior phases (the phase file's "Current state
from earlier phases"). If it doesn't, stop and say so.

Follow the slices in order and commit at every checkpoint, keeping commits atomic: this phase is large. If snippets
have drifted, trust the real files and adapt. Run the full test plan, including
npm run format:check && npm run lint && npm run test && npm run build, before opening the PR.

GitHub: gh is not authenticated here. Use the GitHub MCP tools (ToolSearch "select:mcp__github__create_pull_request,
mcp__github__update_pull_request,mcp__github__add_issue_comment"). Comments end with:

---
_Generated by [Claude Code](https://claude.ai/code)_

Hard rules:
- Never commit vendor firmware (stock .bin/.CDD/.CDI/.spi or vendor zips, or any slice of them), test fixtures
  included.
- Hard interlocks are code.
- User-facing strings are written for an end-user operator: no internal or test-status notes.
- Never touch hardware.

If the phase file has a hardware gate: open the PR, push the branch to dev (git push --force origin HEAD:dev), then
STOP. Return the gate's owner script. Do NOT add the prod-flip slice until you are told the owner confirmed the gate.

Ambiguities: make the smallest reasonable call and record it in the PR. If it would change a name that the
"Cross-phase note" lists, stop and ask.

Return: the PR URL, the branch head SHA, the deviations, the owner gate script (if any), and anything the next phase
must know.

Prior phases (from the orchestrator):
<what earlier phases actually shipped, deviations, the owner's gate results and decisions (e.g. the phase 1 timing numbers)>
```

## B. After a hardware gate (same phase, same branch)

```
Resume phase <N> of the modded firmware flasher series on branch <phase-branch>.
Bootstrap as in the phase file (fresh container), then: git checkout -B <phase-branch> origin/<phase-branch>.
Phase file: $HOME/plan-ref/tmp/features/modded-firmware-flasher/plans/0<N>-*.md

Owner gate result: <OK | FAIL>, verbatim: "<owner's reply>"

If OK: do only the phase file's final "enable … in prod" slice. That is one atomic commit, which must be the last on
the branch. Run the full gates, push, and update the PR body with mcp__github__update_pull_request (tick "prod flag
flipped", and record the gate result).
If FAIL: fix the reported problem with new commits on this branch (no history rewrite), run the gates, push the
branch, push to dev again (git push --force origin HEAD:dev), and STOP. Return the updated owner script. Do NOT flip
the prod flag.

Return: the new head SHA, what changed, and any deviations.
```
