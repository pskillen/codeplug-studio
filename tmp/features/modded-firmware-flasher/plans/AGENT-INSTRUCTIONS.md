# Agent instruction template

The orchestrator uses this block to spawn an `implementor` for one phase. A human can also paste it into a fresh
`implementor` session. Replace every `<…>` placeholder. The orchestrator also appends a "Prior phases" note: what
earlier phases actually did, including deviations from their plan files.

---

```
You are executing phase <N> of 13 of the modded firmware flasher series in pskillen/codeplug-studio.

Your container is fresh. First:
  git fetch origin --prune
  git fetch origin plan/modded-firmware-flasher
  rm -rf "$HOME/plan-ref"; git worktree prune
  git worktree add --detach "$HOME/plan-ref" FETCH_HEAD
Then read and execute exactly one file:
  $HOME/plan-ref/tmp/features/modded-firmware-flasher/plans/<NN>-*.md   (glob it)
That file is self-contained. Do not read sibling phase files, 00-README.md or ../hl-delivery-plan.md unless the
phase file sends you there for a specific detail. Never merge, rebase onto or cherry-pick plan/modded-firmware-flasher
into a product branch.

Branch: <phase-branch>, created with: git checkout -B <phase-branch> <start-ref>
  (<start-ref> is origin/main for phase 1, otherwise origin/<prior-phase-branch>)
PR base: <base-branch>  (stacked; not main unless this is phase 1)
Issue line for the PR body: <Closes #NNNN | Part of #NNNN>

Before the first edit, read AGENTS.md and DESIGN.md at the repo root. Confirm the start ref really contains the
prior phases (the phase file's "Preconditions" lists what to check). If it doesn't, stop and say so.

Follow the phase file's slices in order and commit at every checkpoint (atomic conventional commits). If snippets
or line numbers have drifted, trust the real files and adapt. Run the phase file's full test plan, including
npm run format:check && npm run lint && npm run test && npm run build, before opening the PR.

GitHub: the gh CLI is not authenticated in this container. Use the GitHub MCP tools (load with ToolSearch, e.g.
"select:mcp__github__create_pull_request,mcp__github__add_issue_comment"). Any comment you post ends with:

---
_Generated by [Claude Code](https://claude.ai/code)_

Hard rules: never commit vendor firmware (stock .bin/.CDD/.CDI/.spi or vendor zips, or any slice of them), including
in test fixtures. Hard interlocks are code and never configurable. Do not touch hardware, and do not ask anyone to.
The phase file's "Hardware gate" section, if any, says what the orchestrator does after you finish.

If you hit an ambiguity the phase file does not resolve, make the smallest reasonable call and record it in the PR
description. If it would change a type, signature or file path that a later phase depends on (the phase file's
"Cross-phase note" lists them), stop and ask instead.

When done, return: the PR URL, the branch head SHA, every deviation from the phase file, and anything the next phase
must know.

Prior phases (from the orchestrator):
<summary of what earlier phases actually shipped and any deviations>
```
